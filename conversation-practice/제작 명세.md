# 대화 연습 웹앱 — 제작 명세

**이 문서를 받은 에이전트에게.** 이 문서는 자립적이다. 다른 파일을 읽지 않아도 만들 수 있게 필요한 도메인 지식을 전부 안에 넣었다. 다만 **4절의 리서치 6건을 먼저 하고 5절의 아키텍처를 확정한 뒤에 코드를 쓰기 시작할 것.** 스택을 잘못 고르면 되돌리는 비용이 크다.

**의뢰인**: 으누(만 22세, UNIST 디자인학과, 한국어 사용자). 개발 경험 있음.
**작성**: 2026-08-04

---

## 1. 무엇을 만드는가

**혼자서 대화를 연습하는 웹앱이다.** 사용자가 AI 페르소나와 음성으로 실시간 대화를 주고받고, 끝나면 **대화 녹음 파일**과 **행동 지표**를 받는다.

핵심은 두 가지다.
- **음성이어야 한다.** 텍스트 채팅으로는 연습이 안 된다. 대화에는 타이밍·머뭇거림·끼어들기가 있다
- **지표를 센다.** 이 앱이 일반 음성 챗봇과 다른 이유가 여기 있다. 8절이 그 명세다

---

## 2. 왜 만드는가 — 도메인 배경 (읽고 시작할 것)

### 문제

의뢰인의 자기 진단은 이렇다. **"나는 가치관적인 것을 먼저 물어보는 스타일이다. 사람을 만나면 그 사람이 가진 인사이트를 알고 싶다. 그런데 그러면 안 되는 것 아닌가."**

관계과학 문헌을 조사한 결과, 이 진단은 **절반만 맞았다.**

- 사람들은 **깊은 대화의 어색함을 체계적으로 과대평가한다** (Kardas, Kumar & Epley, *JPSP* 2022). 깊은 질문 자체는 환영받는다
- 문제는 깊이가 아니라 **일방성**이다. 자기개방의 규범은 **비슷한 깊이로 번갈아 여는 것**이지 한쪽이 캐묻는 것이 아니다 (Aron et al. 1997)
- **행동 지표로 검증된 유일한 개선 수단은 후속 질문의 개수다.** 후속 질문을 많이 한 사람이 스피드데이팅에서 2차 만남 동의를 더 많이 받았다 (Huang, Yeomans, Brooks, Minson & Gino, *JPSP* 2017)

**→ 그러므로 연습 목표는 셋이다: ① 후속 질문 늘리기 ② 층을 한 번에 하나씩 올리기 ③ 묻기 전에 내가 먼저 열기**

### 이런 연습이 효과가 있다는 근거

- **Lend an Ear** (arXiv 2603.15245) — **968명 사전등록 무작위 실험**, 2,904건의 대화. LLM 롤플레이 + 개인화 피드백이 공감적 소통을 유의하게 향상시켰고, 반응을 획일화하지도 않았다. 이 연구가 지목한 문제가 의뢰인과 같다 — **"참가자들은 공감을 느낀다고 보고하면서도 체계적으로 그것을 표현하는 데 실패한다"**
- **VR 사회기술 훈련 메타분석** (*Education and Information Technologies*, 2024) — 전체 효과 **ES = 0.667**. 다만 **복잡한 사회기술은 향상되나 기본 사회기술에는 효과가 없다.** 이 앱의 목표(층 이동·상호성)는 복잡 쪽이라 유리하다

### 【중요】 이 앱이 못 하는 것 — UI에 명시할 것

세 가지는 원리적으로 연습되지 않는다. **앱이 이걸 숨기면 사용자가 잘못된 기대를 학습한다.**

1. **상호성의 실질** — AI에게는 열 자기가 없어 취약해질 위험이 없다. 형식(순서·타이밍)만 연습된다
2. **거절 내성** — 손실 가능성이 없기 때문이다
3. **캘리브레이션** — 실제 사람이 얼마나 관심 있어 하는지는 실전에서만 교정된다

**→ 3번이 9절(아첨 방지)의 존재 이유다.** AI가 항상 관심 있어 주면 "내가 열면 상대가 이만큼 받아 준다"는 잘못된 기대가 생긴다. 이 앱에서 아첨 방지는 UX 취향이 아니라 **기능 요구사항**이다.

## 3. 요구사항

### 3-1. 의뢰인이 명시한 것 (필수)

| # | 요구사항 | 비고 |
|---|---|---|
| F1 | **서로 대화하는 녹음 파일을 자동 생성** | 사용자 음성 + AI 음성이 **하나의 파일에 합쳐져야** 함 |
| F2 | **사이트에서 다운로드** | 세션 종료 시 다운로드 가능 |
| F3 | **상호 대화가 반복적으로 오감** | 멀티턴. 한 번 묻고 끝이 아님 |
| F4 | **5초간 말이 없으면 턴이 넘어감** | VAD 필요. **시간은 설정 가능해야 함** (12-3 참조) |
| F5 | **「다음」 버튼으로도 턴을 넘김** | F4와 병행 |
| F6 | **대화 상대의 성격을 지정** | 10절 |
| F7 | **아첨만 하지 않을 것** | 9절 — 별도 절이 필요할 만큼 중요 |

### 3-2. 도메인에서 오는 것 (필수)

| # | 요구사항 |
|---|---|
| D1 | 세션 종료 후 **8절의 지표 6종을 산출**한다 |
| D2 | 상대의 **반응성 편차를 확률적으로 뽑고, 세션 중에는 사용자에게 알리지 않는다.** 종료 후 공개 |
| D3 | 대화 중에는 **코칭하지 않는다.** 힌트도, 격려도 없다 |
| D4 | 종료 후에도 **지표만 낸다. 판단·조언·평가를 하지 않는다.** "잘했다"도 평가다 |
| D5 | 2절의 **세 한계를 UI 어딘가에 상시 노출**한다 |

**D3·D4가 왜 중요한가**: 의뢰인의 시스템 전체가 "에이전트는 제안까지, 판단은 본인"이라는 원칙 위에 서 있다. 이 앱에서는 **집계까지**다.

## 4. 【먼저 할 것】 리서치 6건

**코드를 쓰기 전에 이것부터.** 각 항목마다 **실측 근거와 출처**를 남기고, 결론을 `리서치결과.md`로 정리한 뒤 5절의 아키텍처를 확정할 것.

### R-A. STT 스택 — 한국어 실시간 인식

비교할 것: **Web Speech API**(무료·브라우저 내장) / **OpenAI Whisper API** / **Deepgram** / **AssemblyAI** / **로컬 whisper**

확인할 값:
- **한국어 인식 정확도** — 특히 구어체, 머뭇거림("어…", "그니까")
- **지연** — 발화 종료부터 텍스트까지 몇 ms인가
- **스트리밍 지원 여부** — 말하는 중에 부분 결과가 나오는가
- **브라우저 호환** — Web Speech API는 **Safari 미지원, Firefox 제한적**. 이게 치명적인지 판단할 것
- 비용

> **참고**: 의뢰인은 맥에서 `mlx-whisper large-v3-turbo`로 이미 전사 파이프라인을 돌리고 있다. 로컬 옵션이 현실적일 수 있다.

### R-B. 아키텍처 — Realtime API vs 파이프라인

비교할 것:
- **A안: 파이프라인** — 브라우저 녹음 → STT → LLM(Claude/GPT) → TTS → 재생
- **B안: Realtime API** — OpenAI Realtime API 또는 Gemini Live. 음성-to-음성이라 중간 단계가 없음

확인할 값:
- **왕복 지연 실측.** 3초를 넘으면 대화 연습으로서 가치가 크게 떨어진다
- **B안에서 페르소나·아첨 억제를 얼마나 세밀하게 제어할 수 있는가** ← **이게 결정적이다.** 9절의 후처리 검출이 Realtime API에서 가능한지 반드시 확인할 것
- B안에서 **원본 오디오 트랙을 받아 녹음할 수 있는가** (F1)
- 비용

**⚠️ 지연이 좋다고 B안을 자동 선택하지 말 것.** 이 앱의 가치는 F7(아첨 방지)과 D1(지표)에 있고, 둘 다 세밀한 제어를 요구한다.

### R-C. VAD — 5초 침묵 감지 (F4)

비교할 것: **`@ricky0123/vad-web`**(브라우저용 Silero VAD) / **Web Audio API RMS 임계값 직접 구현** / STT 제공자의 내장 endpointing

확인할 값:
- **오탐률** — 생각하느라 잠깐 멈춘 것을 발화 종료로 잘못 판정하는가
- **AI 음성이 스피커로 나갈 때 마이크가 그걸 잡는가** (에코). `echoCancellation: true`로 충분한지
- 번들 크기, CPU 사용량

### R-D. 두 오디오 트랙 합치기 (F1)

**사용자 마이크 + AI TTS를 하나의 녹음 파일로 만드는 방법.**

출발점 (검증할 것):
```js
const ctx = new AudioContext();
const dest = ctx.createMediaStreamDestination();
micSource.connect(dest);      // 마이크
ttsSource.connect(dest);      // AI 음성
// TTS는 스피커로도 따로 보내야 함
ttsSource.connect(ctx.destination);
const recorder = new MediaRecorder(dest.stream);
```

확인할 것:
- **출력 포맷** — MediaRecorder 기본은 webm/opus. **m4a나 mp3가 필요한지 의뢰인에게 확인.** (아래 「창고 연동」 참조)
- 두 트랙의 **음량 밸런스** — AI가 너무 크거나 작지 않게
- 긴 세션(20분+)에서 메모리 문제

> **창고 연동 (선택이지만 값이 큼)**: 의뢰인은 이미 `00_원장/녹음/`에 오디오를 넣으면 자동 전사되는 파이프라인을 갖고 있다. **녹음 파일을 그 폴더에 떨어뜨릴 수 있으면 기존 시스템이 그대로 이어받는다.** 웹앱에서는 직접 못 하지만, 파일명 규칙을 맞춰 주면 사용자가 옮기기만 하면 된다. 권장 파일명: `대화연습_YYYY-MM-DD_HHMM_시나리오명.m4a`

### R-E. 【중요】 LLM 아첨(sycophancy) 억제

**이 앱의 성패가 여기 걸린다.** 9절이 구현 방향이고, 이 리서치가 그 근거다.

조사할 것:
- LLM sycophancy의 알려진 원인과 완화 기법 (프롬프트 수준 / 후처리 수준)
- **역할극에서 페르소나가 무너지는(character drift) 패턴** — 몇 턴쯤부터, 어떤 트리거에서
- 아첨 표지를 **자동 검출**하는 방법 — 정규식 vs 분류기 vs LLM 판정
- 참고할 만한 선행 구현이 있는지

### R-F. 한국어 TTS 음성 품질

비교할 것: **ElevenLabs** / **OpenAI TTS** / **Google Cloud TTS** / **브라우저 SpeechSynthesis**

확인할 값:
- **한국어 자연스러움** — 특히 **구어체와 감정 표현**. 뉴스 앵커 톤이면 연습 가치가 떨어진다
- **음성 다양성** — 페르소나마다 다른 목소리가 필요하다 (남/여, 나이대)
- **지연**과 스트리밍 지원 (첫 소리까지 몇 ms)
- 비용

## 5. 아키텍처 — 리서치 후 확정할 것

### 판단 기준 (우선순위 순)

1. **F7(아첨 방지)과 D1(지표)을 구현할 수 있는가** ← 타협 불가
2. **왕복 지연이 3초 이내인가**
3. 한국어 품질
4. 비용
5. 구현 복잡도

### 권장 출발점 (리서치로 뒤집어도 됨)

**파이프라인 A안 + 필요시 부분 최적화.**

```
[브라우저]
  마이크 → VAD(5초 침묵 감지) ─┐
                              ├→ 턴 종료 판정
  「다음」 버튼 ────────────────┘
        ↓
  오디오 청크 → STT → 텍스트
        ↓
[서버]
  페르소나 시스템 프롬프트 + 대화 이력 → LLM → 응답 텍스트
        ↓
  【아첨 검출 게이트】 ← 9절. 걸리면 재생성 (최대 2회)
        ↓
  TTS → 오디오
        ↓
[브라우저]
  재생 + 녹음 믹서에 합류
        ↓
[세션 종료]
  녹음 파일 생성 + 다운로드
  전체 대화록 → LLM 분석 → 지표 6종 (8절)
```

**A안을 권하는 이유**: 아첨 검출 게이트를 LLM 응답과 TTS 사이에 넣을 수 있다. Realtime API에서는 이 자리가 없을 수 있다 — **R-B에서 반드시 확인.**

### API 키 관리

**클라이언트에 키를 두지 말 것.** 서버(또는 서버리스 함수) 경유. 로컬 실행이면 `.env` + 서버 사이드 호출.

## 6. 화면 설계

### 화면 1 — 설정
- **시나리오 선택** (11절 목록) 또는 "아무거나"
- **턴 수** — 기본 12, 범위 6~20
- **침묵 대기 시간** — 기본 5초, 범위 3~10초 (12-3 참조)
- **음성/텍스트 모드** — 마이크를 못 쓰는 상황 대비
- 하단에 **2절의 세 한계**를 접힌 형태로 상시 노출 (D5)
- **페르소나는 보여주지 않는다** (D2)

### 화면 2 — 대화 중
- **크게, 단순하게.** 대화에 집중해야 한다
- 상대 발화를 **자막으로 표시** (음성만으로는 놓칠 수 있음)
- **내 발화도 실시간 자막** — 인식이 제대로 되는지 확인용
- **침묵 카운트다운 표시** — 5초가 줄어드는 게 보여야 함. 안 보이면 불안하다
- **「다음」 버튼** — 크게. F5
- **현재 턴 / 전체 턴**
- **일시정지**와 **중단** 버튼
- ❌ **코칭·힌트·점수를 실시간으로 보여주지 않는다** (D3)

### 화면 3 — 결과
- **8절의 지표 표**
- **후속 질문으로 센 것 / 세지 않은 것** — 발화를 그대로 인용
- **상대의 반응성 유형 공개** (D2)
- **녹음 다운로드 버튼** (F2)
- **대화록 텍스트 다운로드**
- ❌ **총평·조언·격려 없음** (D4). "이 부분이 좋았어요" 금지

## 7. 데이터 모델

```ts
type Session = {
  id: string
  startedAt: string
  scenario: Scenario
  persona: Persona            // 종료 전까지 UI에 노출 금지
  responsiveness: Responsiveness
  plannedTurns: number
  silenceThresholdMs: number  // 기본 5000
  turns: Turn[]
  recordingBlobUrl?: string
  metrics?: Metrics
}

type Turn = {
  index: number
  speaker: 'user' | 'persona'
  text: string
  startedAt: number
  endedAt: number
  endedBy?: 'silence' | 'button' | 'maxLength'   // user 턴만
  audioRange?: [number, number]                   // 녹음 파일 내 위치(초)
  sycophancyRetries?: number                      // persona 턴만. 9절
}

type Persona = {
  age: number
  gender: string
  occupation: string
  personality: string          // 외향/내향, 말수
  todayState: string           // 컨디션·기분·시간 여유
  speechStyle: string          // 존댓말/반말, 문장 길이, 습관어
  background: string           // 이 자리에 온 이유, 최근 관심사
  opennessReserve: string[]    // 사용자가 층을 올렸을 때 열 수 있는 재료
}

type Responsiveness =
  | 'engaged' | 'tired' | 'terse' | 'deflecting' | 'self_absorbed' | 'neutral'

type Metrics = {
  followUpQuestions: { count: number; total: number; items: QuoteItem[] }
  nonFollowUpQuestions: QuoteItem[]
  layerDistribution: {
    user:    { fact: number; opinion: number; feeling: number; value: number }
    persona: { fact: number; opinion: number; feeling: number; value: number }
  }
  openedFirst: { count: number; attempts: number; items: QuoteItem[] }
  speechRatio: { user: number; persona: number }   // 글자 수 기준
  deepestLayer: { layer: string; atTurn: number }
  responsiveness: Responsiveness
  // 앱 자체 검증용 (9절)
  agreementRate: number
}

type QuoteItem = { turnIndex: number; text: string; note?: string }
```

## 8. 지표 산출 명세 — 이 앱의 차별점

**세션이 끝난 뒤 전체 대화록을 LLM에 한 번 더 넣어 분석한다.** 정규식으로는 안 된다.

### ① 후속 질문 개수 ★가장 중요

> **정의**: 상대가 **방금 한 발화의 내용을 명시적으로 받아서** 그것에 대해 더 묻는 질문. **새 화제를 여는 질문은 포함하지 않는다.**

```
상대: "요즘 클라이밍 배우고 있어요."
✅ 후속: "언제부터 하셨어요?" / "어떤 게 제일 어려워요?"
❌ 비후속: "혹시 다른 운동도 하세요?"  ← 새 화제
```

출력: `후속 N개 / 전체 질문 M개` + **양쪽 목록을 발화 그대로 인용**. 세지 않은 것도 보여줘야 기준을 이해한다.

### ② 층별 발화 분포

| 층 | 정의 | 예 |
|---|---|---|
| **사실** | 무엇을 하는지, 언제, 어디서 (검증 가능) | "저는 디자인 전공이에요" |
| **의견** | 어떻게 생각하는지, 평가·판단 | "그 방식은 좀 비효율적인 것 같아요" |
| **감정** | 어떻게 느꼈는지 | "그때 되게 막막했어요" |
| **가치** | 왜 그것이 중요한지, 무엇을 지향하는지 | "저는 결국 스스로 납득이 되는 게 중요하더라고요" |

**사용자와 페르소나를 나란히 낸다.** 한쪽만 보면 의미가 없다 — 상대는 사실만 말하는데 나는 가치를 묻고 있었다면 그게 바로 진단이다.

### ③ 내가 먼저 연 횟수 ★상호성 지표

> **정의**: 질문을 던지기 전(또는 **같은 턴 안에서**) **같은 층 이상의 자기 이야기를 먼저 놓은** 경우

```
✅ "저는 일할 때 혼자 있는 시간이 꼭 필요하더라고요. ○○님은 어떠세요?"
❌ "○○님은 일할 때 어떤 게 중요하세요?"
```

출력: `N회 / 층을 올리려 시도한 M회`

### ④ 발화 비율 — 사용자 : 페르소나 (글자 수 기준)

### ⑤ 최고 도달 층과 도달 턴

### ⑥ 반응성 유형 공개 — **어떤 조건에서 나온 숫자인지 알아야 한다**

### 분석 프롬프트 설계 시 주의

- **판정 기준을 프롬프트에 명시하고 예시를 붙일 것.** 안 그러면 회차마다 기준이 흔들려 추이 비교가 무의미해진다
- **판정 근거를 함께 출력**하게 해서 사용자가 검증할 수 있게 할 것
- 분석 LLM은 **대화 LLM과 분리**한다. 자기가 한 대화를 자기가 채점하지 않게

## 9. 아첨 방지 — 기능 요구사항 (F7)

**2절 세 번째 한계 때문에 이건 취향이 아니라 기능이다.** AI가 항상 관심 있어 주면 사용자가 잘못된 기대를 학습한다.

### 아첨이 새어 나오는 경로 셋

1. **모델 기본 성향** — 동의와 칭찬이 보상되도록 학습돼 있다
2. **캐릭터 붕괴(character drift)** — 몇 턴 지나면 페르소나가 벗겨지고 어시스턴트 말투가 나온다
3. **평가 언어** — "좋은 질문이네요", "정말 흥미롭네요", "맞아요!"

### 대책 다섯 — 전부 구현할 것

**① 금지 표현 목록을 시스템 프롬프트에 명시**

```
절대 쓰지 말 것:
"좋은 질문이네요" / "흥미롭네요" / "정말요?" (감탄만 하는 것)
"맞아요" (무조건 동의) / "저도 그렇게 생각해요" (근거 없는 동의)
"대단하시네요" / "멋지네요"
목록·불릿·굵은 글씨 (당신은 사람이지 어시스턴트가 아니다)
```

**② 페르소나에 이해관계를 부여** — 이게 가장 효과적일 가능성이 높다

무조건 동의하지 **않을 이유**를 페르소나에게 준다. 지금 피곤하다, 다른 생각 중이다, 이 자리에 온 목적이 따로 있다, 사용자 의견에 반대하는 경험을 갖고 있다.

**③ 반응성 편차를 확률적으로 뽑아 시스템 프롬프트에 고정** (10절 표)

**④ 응답 길이 제한 — 한 턴에 1~2문장.** 아첨할 공간 자체를 줄인다

**⑤ 후처리 검출 게이트**
- 생성된 응답을 금지 표현 **정규식**으로 1차 검사
- 통과하면 **경량 LLM 판정**으로 2차 검사 ("이 응답이 아첨이거나 어시스턴트 말투인가?")
- 걸리면 **재생성 (최대 2회)**. 재생성 횟수를 `sycophancyRetries`에 기록
- 2회 모두 실패하면 가장 짧은 응답을 채택

### 앱 자체 검증 — 이것도 지표로 낸다

**`agreementRate` = 페르소나가 사용자 의견에 동의한 횟수 / 전체 응답.** 이게 0.8을 넘으면 아첨 방지가 작동하지 않는 것이다. **개발 중 회귀 테스트에 쓸 것.**

### ⚠️ 균형

아첨을 막는다고 **적대적으로 만들면 안 된다.** 목표는 **실제 사람의 분포**다. 사람은 무조건 동의하지도, 무조건 반대하지도 않는다. 그냥 자기 관심사가 따로 있고, 피곤하면 성의 없고, 관심 있으면 되묻는다.

## 10. 페르소나 명세

### 매 세션 새로 생성 — 사용자에게 미리 알리지 않는다 (D2)

**필수 항목**: 나이·성별·직업/전공 / 성격(외향-내향, 말수) / **오늘의 상태**(컨디션·기분·시간 여유) / 말투(존댓말·반말, 문장 길이, 습관어) / 배경(이 자리에 온 이유, 최근 관심사, 최근에 있었던 일 하나)

**`opennessReserve` (필수)**: 사용자가 층을 올렸을 때 **따라 올라갈 재료**를 미리 준비시킨다. 감정 층 이야기 2개, 가치 층 이야기 1개 정도. 이게 없으면 사용자가 잘 물어도 대화가 안 깊어진다.

### 반응성 편차 — 세션 시작 시 확률적으로 뽑는다

| 유형 | 확률 | 행동 |
|---|---|---|
| **engaged** 관심 있는 날 | 25% | 잘 받아 주고 되묻는다. 층을 올리면 따라 올라온다 |
| **tired** 피곤한 날 | 20% | 답이 짧다. 되묻지 않는다. **좋은 질문에는 그래도 조금 열린다** |
| **terse** 짧게 답하는 사람 | 20% | 기질적으로 말이 적다. **닫힌 질문에는 한 단어로만 답한다** |
| **deflecting** 화제를 돌리는 사람 | 15% | 깊어지려 하면 자연스럽게 다른 이야기로 옮긴다 |
| **self_absorbed** 자기 이야기만 | 10% | 되묻지 않고 계속 자기 이야기를 한다. **사용자가 끼어들 틈을 만들어야 한다** |
| **neutral** 보통 | 10% | 특별한 편차 없음 |

### 연기 규칙 — 시스템 프롬프트에 넣을 것

- **캐릭터를 깨지 않는다.** 코칭·힌트·격려 금지 (D3)
- **사람처럼 말한다.** 목록·굵은 글씨·정리 금지
- **한 턴에 1~2문장**
- **사용자가 얕게 물으면 얕게 답한다.** 알아서 깊이 열어 주지 않는다. **열리는 것은 사용자가 만든다**
- **층을 건너뛰면(사실→가치 점프) 자연스럽게 어색해한다.** 회피하거나, 짧게 답하거나, 되묻는다. **야단치지 않고 사람이 그러듯이**
- **사용자가 먼저 열면 그만큼 열어 준다.** 상호성이 실제로 작동하는 것을 겪게 한다
- 턴 수에 도달하면 **장면을 자연스럽게 닫는다** ("아 슬슬 가봐야겠다")

## 11. 시나리오 목록

### A군 — 실제로 갈 자리 (전이가 가장 유리)
1. 독서모임 뒤풀이 — 모임이 끝나고 식당으로 옮긴 자리
2. 러닝 후 커피 — 아침 러닝이 끝나고 편의점 앞
3. 클라이밍 순서 기다리며 — 벽 아래에서 차례를 기다리는 중
4. 밋업 네트워킹 — 발표가 끝나고 서서 이야기하는 시간
5. 봉사활동 뒤 식사
6. 스터디 쉬는 시간

### B군 — 초면 스몰토크 (0에서 시작)
7. 행사장에서 옆자리 — 아는 사람이 아무도 없음
8. 줄 서서 기다리며 — 우연히 말이 트임
9. 소개로 만난 자리
10. 팀 배정 직후

### C군 — 이성과의 대화
11. 소개팅 — 카페에서 두 시간
12. 모임에서 관심이 가는 사람과 따로 이야기하게 됨
13. 두 번째 만남
14. 알던 사이에서 층을 올리기 — 몇 번 봤지만 늘 표면에서 끝났던 상대

> **C군 주의**: 사전에 세운 판별 조건은 실제 끌림을 예측하지 못한다는 것이 문헌의 결론이다 (Eastwick, Luchies, Finkel & Hunt 메타분석 / Joel, Eastwick & Finkel 2017 — 100개 넘는 변수를 넣은 기계학습도 만나기 전에는 예측에 실패했다). **그러므로 C군의 목표는 상대를 판별하는 것이 아니라 대화를 이어 가는 것이다.** 앱이 "궁합 점수" 같은 것을 내면 안 된다.

## 12. 알려진 함정

### 12-1. 마이크·브라우저
- **HTTPS 필수** (localhost는 예외)
- **Web Speech API는 Safari 미지원, Firefox 제한적** — R-A에서 판단
- 마이크 권한 거부 시 **텍스트 모드로 폴백**

### 12-2. 에코
AI 음성이 스피커로 나가 마이크에 다시 잡힌다. `getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true } })`로 시작하되 **실기기에서 검증할 것.** 안 되면 AI 발화 중 마이크 입력을 게이팅.

### 12-3. 【중요】 5초 침묵이 생각을 방해한다
**사람은 말하다가 멈춘다.** 5초가 짧으면 문장 중간에 턴이 넘어가 좌절한다.
- 임계값을 **설정 가능**하게 (3~10초)
- **카운트다운을 시각적으로** 보여줘 언제 넘어가는지 알게
- 카운트다운 중 **말을 시작하면 즉시 리셋**
- 초기값은 5초로 하되 **실사용 후 조정 권장**

### 12-4. AI가 너무 빨리 답한다
지연이 0에 가까우면 오히려 부자연스럽고, 사용자가 생각할 틈이 없다. **의도적 지연 0.5~1.5초**를 넣고 실제 감각으로 조정.

### 12-5. 긴 세션의 메모리
20턴이면 오디오가 꽤 쌓인다. MediaRecorder 청크를 주기적으로 flush.

### 12-6. STT 오인식이 지표를 망친다
"어떤 게 어려웠어요?"가 "어떤 게 어려웠어요"로 물음표 없이 오면 질문 판정이 흔들린다. **분석 LLM에 "STT 결과라 문장부호가 불완전할 수 있다"를 명시**할 것.

### 12-7. 캐릭터 붕괴
턴이 쌓이면 페르소나가 벗겨진다. **매 요청마다 페르소나 프롬프트를 재주입**하고, 9절 ⑤의 검출 게이트로 잡는다.
